# 数据库设计

> 本文按 **`install/database.sql`（39 张表）** 重写。早期草稿里的表结构含 `sessions` 表、
> 主脚本内建 FULLTEXT 索引、以及「`innodb_buffer_pool_size = 2G` + 分表」这类
> 只有独立服务器才谈得上的建议，都与本项目的目标环境（共享虚拟主机）不符。

## 3.1 设计原则

| 原则 | 说明 |
| --- | --- |
| 引擎与字符集 | 全表 `InnoDB` + `utf8mb4` / `utf8mb4_unicode_ci`（支持 emoji，与 MySQL 5.6+/MariaDB 10+ 兼容） |
| 不用 MySQL 8 专有特性 | 不用窗口函数、CTE、`CHECK` 约束、生成列，保证 5.6/5.7/MariaDB 都能建表 |
| **主脚本不含 FULLTEXT** | 部分共享主机的 InnoDB 不支持全文索引；全文索引放在可选的 `install/optional_fulltext.sql` |
| 软删除 | 需要保留历史的表用 `deleted_at`（`NULL` = 未删除）；模型基类里有 `$softDeleteColumn` 显式声明，没有该列的表必须写成 `null` |
| 计数冗余 | `forums.thread_count/post_count`、`threads.reply_count/likes/views`、`users.thread_count/post_count` 都是冗余字段，写操作时增量维护，`CronSvc::update_forum_stats` 定期重算纠偏 |
| 唯一约束即业务规则 | 防重复点赞/收藏/签到/领取任务都靠唯一索引，不靠应用层「先查再插」（并发下会漏） |
| 会话不进数据库 | `SESSION_DRIVER=file`（默认）或 `redis`，**没有 `sessions` 表**；文件在 `storage/sessions/` |
| 表名前缀 | 无前缀，直接 `threads` / `posts`（单库单应用） |

## 3.2 表清单（39 张）

| 模块 | 表 |
| --- | --- |
| 用户 | `users`、`user_groups`、`user_levels`、`user_vip`、`user_checkins`、`user_task_claims`、`social_logins`、`user_blacklist` |
| 论坛内容 | `forums`、`forum_access`、`threads`、`posts`、`post_edit_logs`、`post_likes`、`tags`、`thread_tags`、`tag_categories` |
| 互动 | `messages`、`notifications`、`moments`、`moment_comments`、`moment_likes`、`user_favorites`、`user_follows`、`browse_history` |
| 积分与激励 | `credit_logs`、`rewards` |
| 站点运营 | `announcements`、`friend_links`、`nav_categories`、`nav_links`、`attachments` |
| 系统与安全 | `settings`、`logs`、`sensitive_words`、`ip_blacklist`、`ip_access_logs`、`queue_jobs`、`cluster_nodes` |

> 表清单不是手写的：`scripts/check_schema.php` 会扫描 `app/ core/ resources/ plugins/` 里
> 所有 SQL 引用的表名，逐个核对它们**要么在 `install/database.sql` 里建了、要么运行库里存在**。
> 当初 `social_logins` 就是「代码在用、安装脚本没建」，装了站永远跑不通社交登录，语法检查与冒烟都发现不了。

## 3.3 唯一索引与业务规则

| 表 | 唯一索引 | 挡住的重复 |
| --- | --- | --- |
| `users` | `uk_users_username` / `uk_users_email` / `uk_users_nickname` / `uk_users_api_token` | 用户名 / 邮箱 / 昵称重复、Token 冲突 |
| `post_likes` | `uk_user_thread`、`uk_user_post` | 同一用户重复点赞同一主题/回复 |
| `user_favorites` | `uk_user_thread` | 重复收藏 |
| `user_follows` | `uk_user_follow` | 重复关注 |
| `user_blacklist` | `uk_user_block` | 重复拉黑 |
| `moment_likes` | `uk_moment_user` | 重复点赞动态 |
| `user_checkins` | `uk_user_date` | 同一天重复签到 |
| `user_task_claims` | `uk_user_task_date`（user_id, task_key, claim_date） | 同一任务当天重复领奖 |
| `user_vip` | `uk_user_vip`（user_id） | **一个用户只能有一行会员记录**（历史上是「无有效同行就 INSERT」，过期用户续费直接撞唯一键报「购买失败」） |
| `browse_history` | `uk_user_thread` | 同一帖子只留一条浏览记录（更新 `updated_at` 而不是插新行） |
| `social_logins` | `uk_social_provider_openid` | 同一第三方账号重复绑定 |
| `ip_access_logs` | `uk_ip_action_date` | 同 IP 同行为同一天只留一行计数 |
| `ip_blacklist` | `uk_ip` | 重复封禁 |
| `sensitive_words` | `uk_sensitive_word` | 重复词 |
| `tags` | `uk_tags_name` | 重复标签 |
| `user_levels` | `uk_level` | 等级序号重复 |

写代码时的规矩：**并发场景的「不重复」一律靠唯一索引兜底**，
应用层可以先查（为了给出友好提示），但必须能处理 `Duplicate entry` 异常，
典型做法是 `INSERT ... ON DUPLICATE KEY UPDATE`（如 `ip_access_logs`、`settings`）。

## 3.4 全文索引（可选）

主脚本 `install/database.sql` **刻意不含** FULLTEXT；需要时单独执行：

```bash
mysql -u 用户名 -p 数据库名 < install/optional_fulltext.sql
# 内部执行：
#   ALTER TABLE `threads` ADD FULLTEXT KEY `ft_threads_title_content` (`title`, `content`);
#   ALTER TABLE `posts`   ADD FULLTEXT KEY `ft_posts_content` (`content`);
```

- 不导入也能搜索：`SearchSvc` 会检测索引是否存在，缺失时回退到 `LIKE`。
- **中文短词本来就不靠 FULLTEXT**：MySQL 的默认分词按空格切，中文整句会被当成一个词，
  早期版本因此「搜索静默漏结果」。现在的策略是「有索引且关键词够长走全文，否则走 LIKE」，
  宁可慢一点也不返回空结果。
- 规模再大（十万帖以上）再考虑外部检索引擎；对目标场景（小站）没必要。

## 3.5 共享主机上的注意事项

| 事项 | 建议 |
| --- | --- |
| **不要**改 `innodb_buffer_pool_size` | 共享主机没有 `my.cnf` 修改权限，也不该为单个站点改全局参数 |
| 表数量与体积 | 39 张表，空站约 1–2 MB；真正增长的是 `logs` / `ip_access_logs` / `browse_history` |
| 日志类表的清理 | `CronSvc` 会清理：`logs` 保留 90 天、`ip_access_logs` 保留 7 天；建议配 `/cron/run` |
| 备份 | 面板自带的导出，或 `mysqldump --single-transaction --default-character-set=utf8mb4`（InnoDB 下不锁表） |
| 导入表结构 | 面板的上传 SQL 功能经常限制单文件大小；`install/database.sql` 约 55 KB，一般没问题 |
| 时区 | 全表**没有 `DATETIME`/`TIMESTAMP` 列**：时间统一用 `INT UNSIGNED` 存 Unix 时间戳，应用层统一 `Asia/Shanghai`，从根上避免「数据库时区 vs PHP 时区」不一致（这个坑本项目真踩过：CLI 下是 UTC、Web 下是 +08:00，同一份数据两处显示差 8 小时） |
| 可空列 | 可空列一律写了 `DEFAULT NULL` / `DEFAULT ''`；必填列（如 `created_at`）在插入时由模型/服务显式赋值，不依赖隐式默认值 |

## 3.6 改表流程

数据库变更**不自动迁移**（共享主机上自动改表风险大于收益），按这个顺序做：

1. 改 `install/database.sql`（新装站直接是新的）；
2. 写一段可以重复执行的 `ALTER TABLE` 说明，放进版本发布说明或 `install/` 下的脚本；
3. 用 `php scripts/check_schema.php` 确认代码引用的表都还在；
4. 在目标环境**先备份**再执行 SQL；
5. 跑一遍 `php scripts/smoke.php`（它会真实读写页面与接口）。

新增表时的检查项：

- 表名加入 `docs/03-数据库.md` 的清单（本文 3.2）；
- 模型继承 `App\Models\Model`，`$table` 填表名，没有 `deleted_at` 就写 `protected static ?string $softDeleteColumn = null;`
  （不写会在所有查询里拼出 `deleted_at IS NULL`，直接 1054 报错）；
- 唯一业务约束用 `UNIQUE KEY`，不要只在代码里判断。

## 3.7 分表与归档（现在不做）

早期文档写了「回复表按帖子 ID 哈希分表」「日志按月分表」。这里明确说明**当前没有做，也不建议小站做**：

- `posts` 表分表会把「按主题取回复」「统计回复数」「全文搜索」全部变成跨表查询，
  代码复杂度上升一个量级，而收益要等到百万行级才出现；
- 单表 100 万行、InnoDB + 正确索引在共享主机上依然可用（慢的是全表扫描，不是行数本身）；
- 真正先撑不住的是**日志类表**，而它们可以按时间 `DELETE`（`CronSvc` 已经在做），
  不需要分表。

真到了需要分表的规模，说明已经不该用共享主机了——那时按
[`11-扩展.md`](11-扩展.md) 的路线拆库/加节点，比原地分表更划算。
