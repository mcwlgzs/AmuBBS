# 插件系统实现

> 本文只描述**当前代码里已经实现、并且跑通过真实请求验证**的行为。
> 早期版本这里是「Composer + 依赖注入容器 + EventDispatcher + Plugin 基类 + boot() + 插件市场」的设计稿，
> 那套东西在本项目里没有实现也不打算实现（目标是共享虚拟主机、零依赖），已整体替换。
> 目录里的 `core/EventDispatcher.php`、`core/Validator.php`、`app/Repositories/*` 已经删除。

## 8.1 设计约束与整体结构

### 8.1.1 为什么是这套最简结构

| 约束 | 后果 |
| --- | --- |
| 共享虚拟主机，无 shell / 无 cron / 无 Composer | 不能 `composer require`，不能跑构建，不能常驻进程 |
| 可能没有 Redis | 插件启用状态只能放文件或数据库，这里选文件（不建表、可版本化、坏了也好修） |
| 站长未必懂代码 | 必须能在后台点「启用 / 停用」，而不是手改 JSON |
| 一个坏插件不能拖垮整站 | 加载失败只记日志并跳过，绝不白屏 |

### 8.1.2 文件清单

| 文件 | 职责 |
| --- | --- |
| `core/hooks.php` | 全局函数 `add_action / do_action / add_filter / apply_filters / remove_action / remove_filter / has_action / has_filter`，面向插件作者 |
| `core/Event.php` | 唯一的事件/过滤器调度器（`Core\Event`），同时提供兼容旧 API 的 `listen() / dispatch()` |
| `core/PluginInterface.php` | 插件契约：只强制 `register(): void` |
| `core/PluginManager.php` | 扫描 `plugins/`、读写启用状态、实例化插件、调用生命周期 |
| `core/PluginLoader.php` | 加载已启用插件并调用 `register()`，单个插件失败只跳过 |
| `plugins/Example/` | 自带示例插件（`plugin.json` + `Plugin.php`） |
| `storage/plugin_config/plugins.json` | 启用状态（文件即状态，无需数据库） |
| `app/Controllers/Admin/PluginController.php` | 后台插件管理（列表 / 启用停用 / 卸载） |
| `resources/views/admin/plugins.php` | 后台插件列表页（layuimini 子页面：`layui-card` + `layui-table`） |

自动加载：`core/Bootstrap.php` 的自动加载器把 `Plugins\` 映射到 `plugins/`，
所以 `Plugins\Example\Plugin` → `plugins/Example/Plugin.php`，插件不需要自己的 autoload。

### 8.1.3 一次请求里的启动顺序

```
core/Bootstrap::__construct()
  1. registerAutoloader()          // Core\ -> core/, App\ -> app/, Plugins\ -> plugins/
  2. loadConfig()
  3. require core/hooks.php        // 全局钩子函数（必须早于任何插件）
  4. initSecurity() / initLang()
  5. initRouter()
       └── initEvents()            // 核心自带监听器：LogListener、自动头像、Emoji（优先级 0）
  6. initPlugins()                 // 读 plugins.json -> PluginLoader -> 每个插件的 register()
  7. registerErrorHandler()
  8. 路由分发 -> 控制器/服务 -> Event::dispatch() / apply_filters() 真正触发钩子
```

关键点：

- 钩子函数在第 3 步就绪，插件在第 6 步注册，**业务代码在第 8 步才触发事件**，所以插件永远来得及挂上监听。
- 核心自带监听器走 `Event::listen()`，默认优先级 **0**；插件走 `add_action()`，默认优先级 **10**。
  因此核心监听器（写操作日志等）总是先执行，插件要抢先得显式传更小的优先级。

## 8.2 钩子内核

### 8.2.1 全局函数（插件作者用的是这一层）

```php
add_action(string $tag, callable $callback, int $priority = 10): void
do_action(string $tag, ...$args): void
add_filter(string $tag, callable $callback, int $priority = 10): void
apply_filters(string $tag, mixed $value, ...$args): mixed
remove_action(string $tag, ?callable $callback = null, ?int $priority = null): void
remove_filter(string $tag, ?callable $callback = null, ?int $priority = null): void
has_action(string $tag): bool
has_filter(string $tag): bool
```

语义：

- **优先级**：数字越小越先执行（WordPress 约定），默认 10。
- **Action**：`do_action('tag', $a, $b)` 把参数原样传给每个回调，不关心返回值。
  回调**显式返回 `false`** 会中断后续回调的传播（核心旧 `dispatch()` 就是这个行为，保留了下来）。
- **Filter**：`apply_filters('tag', $value, ...$args)` 让每个回调接收「当前值 + 附加参数」并返回新值，链式传递；没有过滤器时原样返回。
- **移除**：`remove_action('tag')`（回调传 null）会清空该 tag 下的全部回调；传 callable 只移除它。
- `has_action()` 与 `has_filter()` 在本实现里是同一份存储，因此两者等价（内部只有一张 `tag => 优先级 => 回调` 表）。

### 8.2.2 `Core\Event` 静态 API

框架内部和高级用法直接用：

| 方法 | 说明 |
| --- | --- |
| `Event::addAction($tag, $cb, $priority = 10)` | 同 `add_action` |
| `Event::doAction($tag, ...$args)` | 同 `do_action` |
| `Event::addFilter($tag, $cb, $priority = 10)` | 同 `add_filter` |
| `Event::applyFilters($tag, $value, ...$args)` | 同 `apply_filters` |
| `Event::listen($event, $cb, $priority = 0)` | 兼容旧 API，等价 `addAction`（默认优先级 0） |
| `Event::dispatch($event, array $data = [])` | 兼容旧 API，等价 `doAction($event, $data)` |
| `Event::remove($tag)` / `Event::clear()` | 清空某个 tag / 全部（测试用） |
| `Event::hasAction($tag)` / `Event::hasFilter($tag)` / `Event::hasListeners($event)` | 查询 |
| `Event::didAction($tag)` | 该 tag 被 `doAction` 触发过几次（WordPress 的 `did_action`） |
| `Event::count($tag)` / `Event::tags()` | 某 tag 的回调数 / 全部 tag（后台与调试用） |
| `Event::removeAction($tag, ?callable $cb, ?int $priority)` | 精确移除（`core/hooks.php` 的全局函数也支持优先级参数） |

### 8.2.3 兼容层：`listen()` / `dispatch()` 仍然是钩子

旧事件总线用的是 `Event::listen()` + `Event::dispatch()`。
本次改造**没有改任何业务代码**，而是把这两个方法实现成 `addAction` / `doAction` 的别名，
于是已有的 **45 处** `Event::dispatch(Events::X, [...])` 调用点自动变成插件可监听的钩子。

⚠️ 由此带来一个必须知道的形状差异：

```php
Event::dispatch(Events::THREAD_CREATED, ['thread_id' => 12, 'forum_id' => 1]);

// 等价于
do_action('thread.created', ['thread_id' => 12, 'forum_id' => 1]);
//                        ^^^^ 整个数组是一个参数
```

所以 action 回调签名要写成 `function (array $data)`，**不是** `function ($threadId)`。
两个内置监听器的写法都遵循这一点：

```php
add_action('thread.created', function (array $data) {
    $threadId = (int)$data['thread_id'];
});
```

## 8.3 插件契约与生命周期

### 8.3.1 `PluginInterface`

```php
namespace Core;

interface PluginInterface
{
    /** 注册钩子：插件启用后，每次请求都会调用一次 */
    public function register(): void;
}
```

`install()` / `uninstall()` **可选**，不写进接口是有意的（大多数插件不需要）。
两个方法如果存在，则由 `PluginManager` 在对应时机调用（见 8.3.5）。

### 8.3.2 `PluginManager`

```php
$pm = new PluginManager(APP_PATH . 'plugins', APP_PATH . 'storage/plugin_config/');
```

| 方法 | 说明 |
| --- | --- |
| `discover(): array` | 扫描 `plugins/*/plugin.json`，返回 `name => 元数据`（按 name 排序） |
| `all(): array` | 元数据 + `enabled` + `installed_at`，后台列表用 |
| `meta(string $name): ?array` | 单个插件元数据 |
| `getEnabled(): array` | 已启用的插件名（只包含确实被发现的插件） |
| `isEnabled(string $name): bool` | 是否启用 |
| `enable(string $name): bool` | 写状态并（首次）调用 `install()` |
| `disable(string $name): bool` | 写状态，保留 `installed_at`（再次启用不会重复 install） |
| `uninstall(string $name): bool` | 调用 `uninstall()` 后清除状态（**不删插件文件**） |
| `forget(string $name): bool` | 只清状态 |
| `instance(string $name): ?object` | 实例化插件主类（不调用 `register()`），同一请求内只 `new` 一次 |
| `markLoaded()` / `getLoaded()` | 标记/读取「本次请求已加载」的实例 |
| `get(string $name): ?object` | 按名字取已加载实例，忽略大小写与 `-`/`_`（`example` / `Example` / `ex_ample` 都能命中），取不到返回 `null` |

`instance()` 放在 `PluginManager` 而不是 `PluginLoader`：`enable()` / `uninstall()` 需要实例才能调生命周期方法，
两处共用同一份实例缓存，不会重复 `require` 也不会重复 `new`。

### 8.3.3 `PluginLoader`

```php
(new PluginLoader($pluginManager))->load($pluginManager->getEnabled());
```

逐个插件：`instance()` → `register()` → `markLoaded()`。
**一个插件的失败绝不影响其它插件**：文件缺失、类不存在、未实现接口、`register()` 抛异常，都只 `error_log` 后继续下一个。

### 8.3.4 状态文件

`storage/plugin_config/plugins.json`：

```json
{
    "example": {
        "enabled": true,
        "installed_at": 1790313968
    }
}
```

- 不建表、不依赖 Redis：文件存在即状态存在。
- 写入用「临时文件 + `rename()`」原子替换（`plugins.json.{pid}.tmp`），避免并发写坏文件。
- 目录不存在会自动 `mkdir`；写不进去只记日志并返回 `false`，后台会提示检查目录权限。

### 8.3.5 `install()` / `uninstall()` 什么时候跑

| 时机 | 行为 |
| --- | --- |
| 首次 `enable()` | `installed_at` 为空 → 写状态后调用 `install()`，并记下时间戳 |
| 再次 `enable()`（先 disable 过） | `installed_at` 已有值 → **不会**重复调用 `install()` |
| `uninstall()` | 调用 `uninstall()`，然后清掉该插件的状态（插件文件保留，可重新启用） |
| 生命周期抛异常 | 只记日志：`install()` 失败插件仍是启用状态（后台不至于卡死），`uninstall()` 失败也不影响后续请求 |

### 8.3.6 故障隔离

| 故障 | 表现 |
| --- | --- |
| `plugins.json` 不存在 | 视为没有任何插件启用，正常启动 |
| `plugin.json` 缺失 / JSON 损坏 | `discover()` 跳过该目录并记日志 |
| 入口文件缺失 / 类名不对 | `instance()` 返回 `null`，跳过并记日志 |
| 未实现 `PluginInterface` | 跳过并记日志 |
| `register()` 抛异常 | `PluginLoader` 捕获，记日志，其它插件照常 |
| 状态目录不可写 | `enable/disable` 返回 `false`，后台提示检查 `storage/plugin_config/` 权限 |

`admin.*` 事件的载荷统一是「审计日志形状」，因为核心的 `LogListener` 就是靠它写操作日志的：

```php
[
    'action'      => '删除帖子',
    'admin_id'    => 1,
    'detail'      => '删除帖子 ID:12',
    'target_type' => 'thread',
    'target_id'   => 12,
]
```

此外还有一个**框架级钩子**（不属于 `Events` 常量，无参数）：

| 钩子名 | 载荷 | 时机 |
| --- | --- | --- |
| `app.booted` | 无 | 应用就绪后、路由分发前（`Bootstrap::run()`），插件可以在这里挂「每请求执行一次」的逻辑 |

因为插件是在 `app.booted` **之前**加载的（`initPlugins()` 早于 `run()`），插件照样能监听到它。

#### 编辑/删除回复：作者与版主走不同的钩子

`updatePost()` / `deletePost()` 都允许「作者本人」或「版主/管理员」两种身份，但只派发**其中一条**事件，不重复触发：

| 谁在操作 | 触发 |
| --- | --- |
| 作者本人编辑自己的回复 | `post.updated` |
| 版主/管理员编辑别人的回复 | `mod.post.edited` |
| 作者本人删除自己的回复 | `post.deleted` |
| 版主/管理员删除别人的回复 | `mod.post.deleted` |

载荷里 `user_id` 是**执行操作的人**，`author_id` 是**回复作者**。
互斥设计的理由：插件常见的动作是「扣分 / 发通知 / 记审计」，
如果同一个动作触发两条事件，插件就得自己小心去重，很容易重复扣一次分。

### 8.4.2 过滤器（Filter）

当前核心只暴露 **2 个**过滤器，两个都在 `ThreadSvc::createThread()`，且在事务开启**之前**：

| 钩子名 | 值 | 附加参数 | 位置 |
| --- | --- | --- | --- |
| `thread.title` | 标题（已过敏感词） | `$forumId` | `ThreadSvc.php` 发帖流程 |
| `post.content` | 内容（已过敏感词） | `$forumId` | 同上 |

```php
$title   = apply_filters('thread.title', $title, $forumId);
$content = apply_filters('post.content', $content, $forumId);
```

因为过滤发生在写库之前，插件改出来的标题/内容会**原样落库**（已实测：启用示例插件后发帖，数据库里的标题带 `[示例插件]` 后缀）。

### 8.4.3 事件接线现状与自查

`Events` 里的 30 个常量现在全部有派发点。用检查脚本把关：

```bash
php scripts/check_events.php
```

它逐个常量在 `app/ core/ plugins/` 里找 `Event::dispatch(Events::常量名` /
`Events::常量名` 的引用，只出现在 `app/Events/Events.php` 定义处的就是「死钩子」（定义了但永不触发）。
历史上 `post.updated`、`post.deleted`、`mod.thread.locked`、`mod.thread.moved`、
`mod.post.edited`、`mod.post.deleted` 这 6 个长期处于这种状态（文档写着可用、实际永不触发），
已在本轮补齐派发点并逐个用真实请求验证。

## 8.5 后台插件管理

| 路由 | 方法 | 说明 |
| --- | --- | --- |
| `/admin/plugins` | GET | 插件列表（标题、版本、说明、作者、状态、安装时间） |
| `/admin/plugins/toggle` | POST | `name` + `enabled`(1/0)，启用或停用 |
| `/admin/plugins/uninstall` | POST | `name`，调用 `uninstall()` 并清状态 |

页面（`resources/views/admin/plugins.php`）是 layuimini 的 iframe 子页面，
用 `layui-card` + `layui-table` 服务端渲染（**不是** htmx 片段——后台不用 htmx）：

- 状态列显示 `已启用 / 已停用`，另外给「**本次请求已加载**」的插件加一个 `layui-badge layui-bg-blue` 徽章
  ——因为启用只写状态文件，**从下一个请求才开始生效**，页面上的提示文案也按这个事实写。
- 按钮走 `AdminUi.post()` / `AdminUi.confirmPost()`（`public/assets/js/admin-layui.js`，
  内部是 jQuery `$.post` + `layer.confirm`），服务端回 JSON `{code, msg}`，
  成功后 `window.location.reload()` 重载当前子页面。
- 视图里没有任何 `hx-*` 属性；`AdminBase::htmxFlash()` 的 `HX-Trigger: adminFlash` 分支只是
  留给仍带 `HX-Request` 头的外部调用方的兼容路径（见 [`12-后台.md`](12-后台.md) 的交互约定）。

## 8.6 插件静态资源路由

```
GET /plugin-assets/{plugin}/{file:.+}
```

- 插件名只允许 `[A-Za-z0-9_-]`，`file` 里出现 `..` 直接 404 —— 防目录穿越。
- 扩展名白名单：`png jpg jpeg gif webp svg css js woff woff2 ttf eot map json ico`
  —— 明确挡住 `.php` 等可执行后缀，避免插件目录里的源码被当静态文件读出去。
- 先找 `plugins/{Plugin}/assets/{file}`，找不到再找 `plugins/{Plugin}/{file}`。
- 带 ETag（`filemtime-filesize`）+ `Cache-Control: public, max-age=2592000, immutable`，命中 `If-None-Match` 直接 304，不读文件。

## 8.7 如何新增一个钩子

1. 在 `app/Events/Events.php` 加常量，命名建议 `<域>.<对象>.<过去式>`，例如 `thread.moved`。
2. 在业务点 `Event::dispatch(Events::XXX, ['key' => $value, ...])`；一个数组、键名自解释。
   - 需要让插件**修改数据**就用 `apply_filters('域.对象', $值, $上下文)`，并注意位置（写库前还是写库后）。
   - 尽量放在事务提交**之后**，避免插件回调里再开事务。
3. 在 `docs/08-插件系统.md`（本节表格）与 `docs/10-插件开发.md` 的钩子表里补一行。
4. 如果这个时机对插件很重要，给 `plugins/Example/Plugin.php` 或自检脚本补一条断言。

约定：**不修改业务代码**就能让插件生效，是这套钩子存在的唯一理由；
凡是「插件必须改核心文件才能用」的能力，都应该先做成钩子再写插件。

## 8.8 验证方式（实测证据）

| 验证 | 脚本 | 结果 |
| --- | --- | --- |
| 钩子内核 + 插件生命周期单测 | `php scripts/selftest_hooks.php` | **61 项全绿**（含 action/filter 优先级、false 中断、remove、兼容 API、坏插件隔离、install/uninstall 只跑一次、install 抛异常不冒泡） |
| 真实 HTTP 请求里钩子是否生效 | 一次性探针（启用示例插件 → HTTP 发帖 → 查库标题后缀；停用后对照；临时插件回写 `thread.created` 与 `app.booted` 命中） | **30 项全绿** |
| 后台插件管理页 | 一次性探针（登录 → 列表 → 启用 → 下一请求确认已加载 → 停用 → 卸载 → 错误路径 → 还原） | **25 项全绿** |
| 版主/作者事件是否按预期派发 | 一次性探针（管理员发帖回帖 + 普通用户 qaz 回帖，覆盖锁定/移动/作者编辑/版主编辑/作者删除/版主删除六条路径，校验载荷与互斥） | **35 项全绿** |
| 事件常量没有死钩子 | `php scripts/check_events.php` | 30 个常量全部有派发点 |
| 后台页面不白屏 | `php scripts/smoke.php`（含 `/admin/plugins`） | 119 项全绿 |
| 分层纪律 | `php scripts/check_layers.php` | Controllers/Services 零数据访问 |
