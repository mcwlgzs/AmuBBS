# 前端技术选型对比分析

> ⚠️ **历史决策记录**：本文写于项目早期，当时选定 Alpine.js；后来因为目标部署环境是
> 共享虚拟主机（无 root / 无 shell / 无 Node），且页面以内容展示为主，改为
> **htmx 2 服务端渲染片段 + 自研 CSS**（前台不引入 Bootstrap），Alpine.js 已从代码库移除。
> 当前实现与约定见 [07-htmx开发.md](./07-htmx开发.md)。
> 下面的对比与分析保留原样，作为决策过程的记录。

## 当前技术栈（以本节为准，下面的历史分析可能已经过时）

项目现在**前后台是两套独立的技术栈**，这条边界是有意划的：

| | 前台（普通访客） | 后台（`/admin/*`） |
|---|---|---|
| 界面 | 自研 CSS（`public/assets/css/main.css` 等） | **layuimini v2 + Layui 2.6.3** |
| 交互 | htmx 2（服务端渲染片段） | Layui（`table.render` + `layer` 弹层） |
| 页面形态 | 整页 HTML | 外壳（iframe 多 tab）+ 每个页面一个完整子文档 |
| 图标 | 内联 SVG / emoji | Font Awesome 4.7（layuimini 的图标体系） |
| 依赖体积 | 极简 | layui + layuimini + font-awesome，只在后台加载 |

几条硬约束没有变：**无 root / 无 shell / 无 Node、无构建步骤、资源全部本地 vendored 不依赖 CDN。**

### 后台为什么是 layuimini

后台经历过三次形态，这里记一下，免得再来回改：

1. **Layui + iframe 多 tab（早期）** —— 本项目最初的实现，后被下面的方案取代。
2. **AdminLTE 4 → Tabler 1.5 + htmx 局部替换** —— 去掉 iframe，`#admin-main` 整体替换，
   一次导航一个请求。视觉换了两轮，仍然是 Bootstrap 系。
3. **layuimini v2（Layui 2.6.3，iframe 多 tab，当前）** —— 回到 iframe 形态，
   取的是 layuimini 开箱即用的**多 tab 多窗口、无限级菜单、五套配色**，
   以及 Layui 自带且成熟的数据表格 / 弹层 / 表单组件；
   代价是放弃 htmx 的单请求导航，并重新引入 Layui。

### 需要注意的边界

- **layui 只能出现在后台。** 前台 HTML 里不允许出现 layui ——
  这条规则由 `scripts/smoke.php` 的「前台 HTML 不含 layui」断言守着。
- 后台的 JSON 接口（`/admin/api/*`）返回的是 Layui 表格约定的
  `{code, msg, data, count}`，这是历史约定，不要改成别的形状。
- 后台子页面**永远是完整文档**，不再按 `HX-Request` 返回片段
  （`scripts/smoke.php` 有对应断言，防止片段模式被加回来）。
- htmx 现在只服务前台；后台的 `hx-*` 属性应当全部消失。

## 6.0 实测数据与决策依据（后补，按当前代码实测）

6.1 之后的对比是**写代码之前**的推演。下面是拿真实页面量出来的数据，
用来回答「前台要不要也换成 Bootstrap 5」这个问题。

### 6.0.1 怎么量的

1. 抓真实页面 HTML（游客态），解析出 `<link rel=stylesheet>` 与 `<script src>`；
2. 逐个累加 `public/assets/` 下的本地文件大小（外链为 0，本项目不走 CDN）；
3. 用等价的 gzip -9 压缩得到**实际传输体积**（原始体积只作参考，服务器会开 gzip）。

### 6.0.2 前台每页实际体积（gzip 后）

| 页面 | CSS | JS | 合计 |
| --- | --- | --- | --- |
| 首页 `/`（游客，最坏情况） | 19.1 KB | 39.4 KB | **58.5 KB** |
| 板块页 `/forum/1` | 24.5 KB | 39.4 KB | **63.9 KB** |
| 帖子详情 `/thread/1` | 18.9 KB | 39.4 KB | **58.3 KB** |
| 登录 / 注册 | 14.5 KB | 39.4 KB | **53.9 KB** |

其中 JS 的固定开销是 htmx 16.9 KB(gzip) + app.js 12.4 KB + 其余小库约 9 KB；
CSS 里 `main.css` 8.2 KB + 页面级 CSS（index 4.9 / thread 4.2 KB）+ 游客的 `auth.css` 3.5 KB。

### 6.0.3 如果前台改用后台那套 Tabler 1.5（内含 Bootstrap 5）

| 资源 | 原始 | gzip |
| --- | --- | --- |
| `tabler.min.css`（含 Bootstrap 5 全部组件样式） | 678 KB | **80.4 KB** |
| `tabler.min.js`（含 Bootstrap JS + Popper） | 83 KB | **25.1 KB** |
| `bootstrap-icons.min.css`（图标字体 CSS；字体文件另计 131 KB 不可压） | 85 KB | **13.9 KB** |
| 合计需额外下载 | 846 KB | **≈120 KB** |

也就是说：前台一旦引入 Bootstrap 5，**每页传输体积大致变成现在的 3 倍**（58 → ~178 KB gzip），
而且**没法 tree-shaking** —— 项目不允许 Node/构建步骤，只能整包引入。

### 6.0.4 类名冲突的面有多大

自研 CSS 大量使用了 Bootstrap 的类名，但语义与实现是自己的一套：

| 类名 | 前台视图里出现 | 自研 CSS 里定义 |
| --- | --- | --- |
| `btn` | 112 次 | 44 处 |
| `card` | 88 次 | 22 处 |
| `nav-*` | 24 次 | 32 处 |
| `dropdown` | 14 次 | 11 处 |
| `pagination` | 2 次 | 13 处 |
| `badge` | 3 次 | 11 处 |
| 其它（container/row/modal/progress…） | 25 次 | 25 处 |
| **合计** | **268 次（63 个前台视图）** | **158 处** |

两套定义同时存在 → 这些类名会互相覆盖，视觉几乎必然错乱。
所以「前台引入 Bootstrap」不是加一行 `<link>`，而是**重写 63 个前台视图 + 重做 158 处样式定义**。

### 6.0.5 结论与建议

| 方案 | 每页 gzip | 改造成本 | 风险 |
| --- | --- | --- | --- |
| **A. 保持现状**（htmx + 自研 CSS） | ~58 KB | 0（已上线） | 无 |
| B. 前台换 Bootstrap 5/Tabler | ~178 KB | 重写 63 个视图 + 158 处样式 | 类名冲突、体积 3 倍、与「小机器/共享主机」目标相悖 |
| C. 只借 Bootstrap 的工具类子集（自己裁一份 grid/utility） | 视裁剪，可控 | 中（要维护裁剪脚本或手抄子集） | 中（等于自己维护框架子集） |

**建议 A**，并按需继续做「只有用到才加载」的优化 —— 这才符合本项目的目标（共享主机、1C1G 也跑得动）。
本轮已经落地的实测优化：

| 优化 | 效果 |
| --- | --- |
| 验证码资源（`captcha.css` + 阻塞的 `captcha.js`）只在站点启用验证码时加载 | 关掉验证码的站点每页 **-12.7 KB 原始 / -3.8 KB gzip**，并少一次**阻塞渲染**的 `<head>` 脚本请求 |
| `auth.css` 仅游客加载（早已实现） | 已登录用户每页 -17.2 KB 原始 / -3.5 KB gzip |

如果确实要让前台也用 Bootstrap（例如为了 contributors 熟悉度或统一后台前台范式），
前提是先接受上面第 6.0.3 与 6.0.4 的代价，并同步更新
[`07-htmx开发.md`](./07-htmx开发.md) 与 `docs/12-后台.md` 的约定。

## 6.1 技术方案对比

你提到的两个方案对比：

| 维度 | Xiuno BBS 方案 | AMuBBS 方案（实际采用） | 更优方案推荐 |
|------|----------------|-------------|--------------|
| **前端框架** | Bootstrap 4 + jQuery 3 | htmx 2 + 自研 CSS（零构建） | 无构建步骤 + 服务端渲染片段 |
| **插件系统** | Hook + Overwrite | WordPress 风格钩子（add_action / apply_filters） | 零依赖 + 事件与过滤器 |

## 6.2 前端框架深度对比

### 6.2.1 方案一：Bootstrap 4 + jQuery 3（Xiuno BBS）

**优点：**
- ✅ 成熟稳定，社区资源丰富
- ✅ 学习成本低，上手快
- ✅ 兼容性好，支持老旧浏览器
- ✅ UI 组件开箱即用

**缺点：**
- ❌ jQuery 性能较差（DOM 操作频繁）
- ❌ Bootstrap 体积大（~150KB）
- ❌ 不适合复杂交互（状态管理混乱）
- ❌ 技术栈老旧，不利于长期维护

**适用场景：**
- 简单的内容展示型网站
- 需要快速开发的小型项目
- 团队对现代前端框架不熟悉

### 6.2.2 方案二：原生 JS + Alpine.js（AMuBBS 初始方案）

**优点：**
- ✅ 极致轻量（Alpine.js 仅 15KB）
- ✅ 无构建步骤，开发简单
- ✅ 性能优秀（接近原生）
- ✅ 学习成本低

**缺点：**
- ❌ 缺少完整的生态系统
- ❌ 复杂状态管理困难
- ❌ 组件复用性差
- ❌ 缺少开发工具支持（调试、热更新等）
- ❌ 大型项目维护困难

**适用场景：**
- 极简的静态网站
- 需要渐进式增强的传统网站
- 对包体积有极致要求的项目

### 6.2.3 方案三：Vue 3 + Vite（⭐ 推荐方案）

**优点：**
- ✅ 现代化框架，性能优秀
- ✅ 组件化开发，代码复用性强
- ✅ 响应式系统，状态管理清晰
- ✅ 完整的生态系统（Vue Router、Pinia）
- ✅ 优秀的开发体验（热更新、TypeScript 支持）
- ✅ 构建产物可优化（Tree Shaking、代码分割）
- ✅ 学习曲线平缓（相比 React）

**缺点：**
- ❌ 需要构建步骤
- ❌ 学习成本略高于 jQuery
- ❌ 首次加载需要加载框架代码（~50KB gzipped）

**适用场景：**
- 中大型单页应用
- 需要复杂交互的论坛系统
- 长期维护的项目

**性能对比：**

| 指标 | jQuery | Alpine.js | Vue 3 |
|------|--------|-----------|-------|
| **包体积（gzipped）** | ~30KB | ~15KB | ~50KB |
| **首次渲染** | 慢 | 快 | 快 |
| **更新性能** | 慢 | 中 | 快 |
| **内存占用** | 高 | 低 | 中 |
| **开发效率** | 低 | 中 | 高 |

### 6.2.4 方案四：React + Next.js（备选方案）

**优点：**
- ✅ 生态最丰富
- ✅ SSR 支持好（SEO 友好）
- ✅ 大公司背书，长期维护有保障

**缺点：**
- ❌ 学习曲线陡峭
- ❌ 包体积较大
- ❌ 需要掌握 JSX、Hooks 等概念

**适用场景：**
- 需要 SSR 的大型项目
- 团队已有 React 经验

## 6.3 插件系统深度对比

### 6.3.1 方案一：Hook + Overwrite（Xiuno BBS）

**实现示例：**
```php
<?php
// 注册钩子
hook_add('thread_create_before', function($data) {
    // 在创建帖子前执行
    $data['title'] = filterSensitiveWords($data['title']);
    return $data;
});

// 覆盖方法
function thread_create($data) {
    // 插件可以完全覆盖这个函数
}
```

**优点：**
- ✅ 实现简单
- ✅ 灵活性高（可以完全覆盖原函数）

**缺点：**
- ❌ 插件间可能冲突（多个插件覆盖同一函数）
- ❌ 调试困难（不知道哪个插件修改了行为）
- ❌ 性能开销大（每次调用都要检查钩子）
- ❌ 缺少依赖管理

### 6.3.2 方案二：事件驱动 + 依赖注入（AMuBBS 初始方案）

**实现示例：**
```php
<?php
// 定义事件
class ThreadCreatedEvent
{
    public function __construct(
        public int $threadId,
        public int $userId
    ) {}
}

// 监听事件
class NotificationListener
{
    public function handle(ThreadCreatedEvent $event): void
    {
        // 发送通知
        NotificationService::send($event->userId, '帖子创建成功');
    }
}

// 触发事件
event(new ThreadCreatedEvent($threadId, $userId));
```

**优点：**
- ✅ 解耦性好（事件发布者不需要知道监听者）
- ✅ 易于测试
- ✅ 支持异步处理

**缺点：**
- ❌ 事件流程不直观（需要查找监听器）
- ❌ 缺少插件生命周期管理
- ❌ 插件间依赖关系不明确

### 6.3.3 方案三：事件驱动 + 插件容器（⭐ 推荐方案）

**实现示例：**
```php
<?php
// 插件接口
interface PluginInterface
{
    public function getName(): string;
    public function getVersion(): string;
    public function getDependencies(): array;
    public function boot(): void;
    public function register(): void;
}

// 插件基类
abstract class Plugin implements PluginInterface
{
    protected EventDispatcher $events;
    protected Container $container;

    public function __construct(EventDispatcher $events, Container $container)
    {
        $this->events = $events;
        $this->container = $container;
    }

    public function getDependencies(): array
    {
        return [];
    }
}

// 示例插件
class NotificationPlugin extends Plugin
{
    public function getName(): string
    {
        return 'notification';
    }

    public function getVersion(): string
    {
        return '1.0.0';
    }

    public function register(): void
    {
        // 注册服务到容器
        $this->container->singleton(NotificationService::class);
    }

    public function boot(): void
    {
        // 注册事件监听器
        $this->events->listen(ThreadCreatedEvent::class, function($event) {
            $this->container->get(NotificationService::class)->send($event);
        });
    }
}

// 插件管理器
class PluginManager
{
    private array $plugins = [];
    private array $booted = [];

    public function register(Plugin $plugin): void
    {
        // 检查依赖
        foreach ($plugin->getDependencies() as $dependency) {
            if (!isset($this->plugins[$dependency])) {
                throw new Exception("插件 {$plugin->getName()} 依赖 {$dependency}");
            }
        }

        $this->plugins[$plugin->getName()] = $plugin;
        $plugin->register();
    }

    public function boot(): void
    {
        foreach ($this->plugins as $plugin) {
            if (!in_array($plugin->getName(), $this->booted)) {
                $plugin->boot();
                $this->booted[] = $plugin->getName();
            }
        }
    }

    public function enable(string $name): void
    {
        // 启用插件
    }

    public function disable(string $name): void
    {
        // 禁用插件
    }
}
```

**优点：**
- ✅ 完整的插件生命周期管理
- ✅ 依赖注入，易于测试
- ✅ 支持插件间依赖声明
- ✅ 事件驱动，解耦性好
- ✅ 可以动态启用/禁用插件
- ✅ 插件隔离，避免冲突

**缺点：**
- ❌ 实现复杂度较高
- ❌ 需要理解依赖注入和事件系统

**适用场景：**
- 需要丰富插件生态的系统
- 长期维护的项目
- 需要第三方开发者贡献插件

### 6.3.4 方案四：微内核架构（备选方案）

**特点：**
- 核心系统只提供最基础功能
- 所有功能都以插件形式存在
- 插件可以相互通信

**适用场景：**
- 需要极致灵活性的系统
- 不同客户需要不同功能组合

## 6.4 最终推荐方案

### 6.4.1 前端技术栈

**推荐：原生 JS + Alpine.js**

**理由：**
1. **极致轻量**：Alpine.js 仅 15KB，无需构建步骤
2. **性能优秀**：接近原生 JS 性能，响应速度快
3. **学习成本低**：类 Vue 语法，上手快速
4. **部署简单**：无需 Node.js 环境，直接引入 CDN
5. **适合论坛场景**：论坛以内容展示为主，不需要复杂的前端框架

**技术栈：**
```html
<!-- 通过 CDN 引入 -->

<!-- 可选：Axios 用于 API 请求 -->

```

**项目结构：**

### 6.4.2 插件系统

**推荐：事件驱动 + 插件容器 + 依赖注入**

**核心特性：**
1. **插件生命周期**：register → boot → shutdown
2. **依赖管理**：自动解析插件依赖关系
3. **事件系统**：插件通过事件通信
4. **服务容器**：依赖注入，易于测试
5. **热插拔**：支持动态启用/禁用插件

**插件示例：**
```php
<?php
// plugins/EmailNotification/EmailNotificationPlugin.php

class EmailNotificationPlugin extends Plugin
{
    public function getName(): string
    {
        return 'email-notification';
    }

    public function getVersion(): string
    {
        return '1.0.0';
    }

    public function getDependencies(): array
    {
        return ['notification']; // 依赖通知插件
    }

    public function register(): void
    {
        // 注册邮件服务
        $this->container->singleton(EmailService::class, function() {
            return new EmailService(config('mail'));
        });
    }

    public function boot(): void
    {
        // 监听通知事件
        $this->events->listen(NotificationCreatedEvent::class, function($event) {
            $emailService = $this->container->get(EmailService::class);
            $emailService->send($event->user->email, $event->content);
        });
    }

    public function getConfig(): array
    {
        return [
            'smtp_host' => 'smtp.example.com',
            'smtp_port' => 587,
            'from_email' => 'noreply@amubbs.com',
        ];
    }
}
```

## 6.5 混合方案（渐进式升级）

如果担心一次性切换到 Vue 3 风险太大，可以采用**渐进式升级**策略：

### 阶段一：原生 JS + Alpine.js（MVP）
- 快速上线核心功能
- 使用 Alpine.js 处理简单交互
- 静态页面为主

### 阶段二：局部引入 Vue 3
- 复杂交互模块使用 Vue 3（如富文本编辑器、实时通知）
- 其他部分保持 Alpine.js
- 两者可以共存

### 阶段三：全面迁移到 Vue 3
- 逐步将所有页面迁移到 Vue 3
- 统一技术栈，提升维护性

**共存示例：**
```html
<!-- Alpine.js 处理简单交互 -->
<div x-data="{ open: false }">
    <button @click="open = !open">切换</button>
    <div x-show="open">内容</div>
</div>

<!-- Vue 3 处理复杂组件 -->
<div id="editor-app"></div>
<script type="module">
import { createApp } from 'vue'
import Editor from './components/Editor.vue'

createApp(Editor).mount('#editor-app')
</script>
```

## 6.6 总结建议

**前端框架：**
- ⭐ **首选**：原生 JS + Alpine.js（极致轻量、性能优秀、无需构建）
- 🔄 **备选**：原生 JS + Petite-Vue（类 Vue 语法，仅 6KB）
- ❌ **不推荐**：jQuery（技术栈老旧，性能较差）

**插件系统：**
- ⭐ **首选**：事件驱动 + 插件容器 + 依赖注入（功能完整、易扩展）
- 🔄 **备选**：简单的事件驱动（实现简单，适合小型项目）
- ❌ **不推荐**：Hook + Overwrite（容易冲突，调试困难）

**实施建议：**
1. **全程使用 Alpine.js**：论坛系统以内容展示为主，Alpine.js 完全够用
2. **复杂组件模块化**：将富文本编辑器、实时通知等封装为独立模块
3. **渐进增强**：先实现核心功能，再逐步添加交互效果
